# AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기

2차원 패턴이 십자가(Cross)인지 X인지를 MAC(Multiply-Accumulate) 연산으로 판별하는
Mini NPU 시뮬레이터입니다. 외부 라이브러리 없이 파이썬 표준 기능만 사용했습니다.

## 실행방법

### 준비물

- Python 3.8 이상
- 외부 라이브러리 설치 불필요 (`json`, `time` 등 표준 라이브러리만 사용)

### 파일 구성

| 파일 | 역할 |
| --- | --- |
| `main.py` | 실행 파일. 입력, 판정, 성능 측정, 화면 출력 담당 |
| `mac_calc.py` | MAC 연산과 연산 시간 측정 담당 (`MacCalc`) |
| `data_loader.py` | JSON 읽기와 라벨 정규화, 스키마 검사 담당 |
| `pattern_maker.py` | 십자가/X 패턴 생성 담당 (`PatternMaker`, 보너스) |
| `data.json` | 필터(size_3 / size_5 / size_13 / size_25)와 패턴 8개 |

역할을 세 파일로 나눴습니다.
`data_loader.py`가 "읽고 정리하는 일"을, `mac_calc.py`가 "계산하는 일"을,
`main.py`가 "판정하고 보여주는 일"을 맡습니다.
그래서 데이터 형식이 바뀌면 `data_loader.py`만, 계산 방식을 바꾸고 싶으면
`mac_calc.py`만 고치면 됩니다.

### 실행

`data.json`이 있는 폴더에서 아래 명령을 실행합니다.

```
python main.py
```

실행하면 모드를 고릅니다.

- `1` : 사용자 모드 (직접 입력 / 패턴 자동 생성)
- `2` : data.json 분석

#### 모드 1 (사용자 모드)

패턴을 어디서 가져올지 한 번 더 고릅니다.
어느 쪽을 골라도 그 뒤 판정과 성능 측정은 똑같은 경로를 지납니다.

```
선택: 1

[입력 방식 선택]
1. 직접 입력 (3x3)
2. 패턴 자동 생성 (보너스)
선택:
```

**1. 직접 입력** — 필터 A, 필터 B, 패턴을 각각 3줄씩 공백으로 구분해 입력합니다.

```
선택: 1
필터 A (3줄 입력, 공백 구분)
0 1 0
1 1 1
0 1 0
필터 B (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
패턴 (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
```

줄마다 숫자 개수가 3개가 아니거나 숫자가 아닌 값이 들어오면
오류 문구를 보여주고 그 행렬을 처음부터 다시 입력받습니다.
사용자가 넣은 필터라 어느 쪽이 정답인지 알 수 없으므로 판정 결과만 보여줍니다.

**2. 패턴 자동 생성 (보너스)** — 크기 N과 모양을 고르면
그 크기의 십자가/X 필터와 패턴을 만들어 판정과 성능 측정까지 합니다.

```
선택: 2
크기 N 을 입력하세요 (1 이상): 7

만들 패턴의 모양을 고르세요.
1. 십자가 (Cross)
2. X
선택: 2
```

`data.json`에 없는 크기(7x7, 9x9 등)도 만들어 볼 수 있습니다.
이쪽은 어떤 모양으로 만들었는지 알고 있으므로 PASS/FAIL까지 보여줍니다.

#### 모드 2 (data.json 분석)

```
python main.py
선택: 2
```

필터 로드 → 패턴별 판정(PASS/FAIL) → 성능 분석 표 → 결과 요약 순으로 출력합니다.

## 구현요약

### 1. MAC 연산 (`mac_calc.py`)

`MacCalc` 클래스가 계산과 관련된 일을 모두 맡습니다.

| 이름 | 역할 |
| --- | --- |
| `MacCalc.calculate_2d_array(pattern, filter)` | MAC 연산 한 번 |
| `MacCalc.measure_time_2d_array(pattern, filter)` | 같은 연산을 반복해 평균 시간 측정 |
| `REPEAT_COUNT` | 측정 반복 횟수 (10회) |

`calculate_2d_array`는 NumPy 같은 라이브러리를 쓰지 않고 이중 `for` 문으로 직접 계산합니다.

```
for row in range(len(pattern)):
    for col in range(len(pattern[row])):
        total = total + pattern[row][col] * filter[row][col]
```

계산 전에 행 개수와 각 행의 열 개수가 같은지 확인하고,
다르면 `ValueError`를 냅니다. 이 오류는 `main.py`에서 잡아서
프로그램을 멈추지 않고 그 케이스만 FAIL로 처리합니다.

시간 측정도 같은 클래스에 넣었습니다. 재는 대상(MAC 연산)과 재는 도구가 한곳에 있어야
계산 방식을 바꿔도 측정 조건이 어긋나지 않기 때문입니다.
메서드 이름에 `_2d_array`를 붙여 둔 것도 같은 이유입니다. 보너스 과제인 1차원 배열
최적화 버전은 `calculate_1d_array` / `measure_time_1d_array`를 같은 클래스에 나란히
추가하면, 똑같은 `REPEAT_COUNT`와 똑같은 측정 방식으로 두 방법을 비교할 수 있습니다.

### 2. 라벨 정규화 (`data_loader.py`)

`data.json`은 필터를 `cross` / `x`로, 정답을 `+` / `x`로 서로 다르게 적어 둡니다.
그대로 비교하면 `'x'`가 필터 키인지 정답인지 헷갈리고, `'+'`와 `'cross'`는
같은 뜻인데도 문자열이 달라 항상 FAIL이 납니다.

그래서 읽어오는 순간 표준 라벨 두 가지(`Cross`, `X`)로 통일합니다.

| 원본 | 위치 | 표준 라벨 |
| --- | --- | --- |
| `cross` | filters 키 | `Cross` |
| `x` | filters 키 | `X` |
| `+` | expected 값 | `Cross` |
| `x` | expected 값 | `X` |

정규화 이후의 출력과 PASS/FAIL 비교는 전부 `Cross` / `X` 기준으로만 합니다.
표에 없는 값(예: `circle`)이 들어오면 그 케이스만 FAIL로 처리하고 계속 진행합니다.

패턴은 읽어오는 단계에서 아래 세 가지를 미리 검사해 둡니다.

- `input` 또는 `expected` 항목이 있는가
- 이름(`size_5_1`)에서 크기를 읽을 수 있는가
- `expected` 값이 아는 라벨인가

문제가 있으면 그 자리에서 멈추지 않고 `error` 항목에 사유만 적어 둡니다.
`main.py`는 `error`가 비어 있지 않으면 그 케이스만 FAIL로 기록하고 다음으로 넘어갑니다.
그래서 데이터가 조금 깨져 있어도 프로그램 전체가 죽지 않습니다.

### 3. 동점 처리 정책 (epsilon)

점수가 실수(float)라서 `==`나 `>`로 그냥 비교하면 안 됩니다.
그래서 아래 규칙을 씁니다.

```
EPSILON = 1e-9

judge(first_score, second_score, first_label, second_label)

차이가 EPSILON 보다 작으면  -> UNDECIDED (판정 불가)
앞쪽 점수가 더 크면         -> first_label
그 외                       -> second_label
```

이 규칙은 `main.py`의 `judge()` 한 곳에만 있습니다.
라벨을 인자로 받기 때문에 자동 생성·data.json 분석은 `'Cross'`/`'X'`로,
직접 입력은 `'A'`/`'B'`로 같은 함수를 그대로 씁니다.
동점 기준이 갈래마다 어긋날 일이 없습니다.

`UNDECIDED`는 `Cross`도 `X`도 아니므로 expected와 절대 같아질 수 없고, 항상 FAIL이 됩니다.
이는 "정답을 모르는 상태"를 정답인 척 넘기지 않겠다는 의도적인 선택입니다.

### 4. 성능 측정 기준

- 측정은 `MacCalc.measure_time_2d_array()`가 담당합니다.
- 각 크기마다 MAC 연산을 10회(`REPEAT_COUNT`) 반복한 뒤 평균 시간을 ms로 출력합니다.
- `time.perf_counter()`로 **MAC 함수 호출 구간만** 감쌉니다.
  입력받기, 파일 읽기, 화면 출력 시간은 측정에 넣지 않습니다.
- 재는 대상은 `data.json`에 실제로 있는 필터와 패턴뿐입니다.
  어떤 크기에 필터만 있고 패턴이 없으면 없는 값을 지어내지 않고 `건너뜁니다`를 출력합니다.

### 5. data.json 에 크기 3 추가

명세 「9. 실행 흐름」은 data.json 분석 모드에서도 3x3을 요구합니다.

> data.json 분석 모드: … → 성능 분석(**3×3 포함**, 5×5/13×13/25×25) 출력 → 결과 요약 출력

그런데 원본 `data.json`에는 5, 13, 25만 있었습니다. 3x3을 코드 안에 상수로 박아 두거나
프로그램이 만들어 쓸 수도 있었지만, 그러면 3x3만 다른 경로를 타게 되어
"data.json 분석 모드"인데 data.json에 없는 값을 재는 모양이 됩니다.

그래서 `data.json`에 아래를 추가했습니다. 값은 명세 「1. 미션 소개」의 예시 배열 그대로이고,
키 이름과 라벨 규칙(`_1`은 `x`, `_2`는 `+`)은 기존 항목과 맞췄습니다.

| 추가한 키 | 내용 |
| --- | --- |
| `filters.size_3` | `cross` = 십자가, `x` = X (3x3) |
| `patterns.size_3_1` | X 패턴, `expected` = `x` |
| `patterns.size_3_2` | 십자가 패턴, `expected` = `+` |

덕분에 3x3도 5/13/25와 완전히 같은 경로로 로드·판정·측정되며,
크기 3을 위한 예외 처리 코드가 프로그램에 하나도 없습니다.

이 두 케이스의 점수는 명세 「1. 미션 소개」의 Case 1(5점) / Case 2(1점)와 정확히 일치합니다.

### 6. 패턴 자동 생성을 모드로 두지 않은 이유

패턴 자동 생성은 별도 모드가 아니라 **사용자 모드 안의 분기**입니다.

모드로 두면 "패턴을 받아 → MAC 연산 → 판정 → 성능 측정"이라는 흐름이
두 벌로 복제됩니다. 실제로 두 갈래가 다른 부분은 앞쪽 **패턴을 어디서 얻는가**뿐이고,
그 뒤는 완전히 같습니다. 그래서 앞쪽만 함수 두 개로 나누고,
둘 다 같은 모양의 `setup` 하나를 만들어 돌려주게 했습니다.

| 키 | 직접 입력 | 자동 생성 |
| --- | --- | --- |
| `pattern` / `first_filter` / `second_filter` | 사용자가 입력한 3x3 | 생성기가 만든 NxN |
| `first_label` / `second_label` | `A` / `B` | `Cross` / `X` |
| `expected` | `None` (정답을 모름) | 만든 모양 (정답을 앎) |
| `steps` | `2` (필터 입력, 패턴 입력) | `1` (패턴 생성) |

```
input_source()
   ├─ build_setup_by_input()      ─┐
   └─ build_setup_by_generator()  ─┴─> setup ─> print_setup_verdict()
                                                print_setup_performance()
```

`expected`가 `None`이면 판정만, 값이 있으면 `PASS`/`FAIL`까지 출력합니다.
`steps`는 갈래마다 이미 쓴 단계 번호 개수라, 뒤쪽에서 `[3] MAC 결과` / `[2] MAC 결과`처럼
번호를 이어 붙이는 데 씁니다. 덕분에 MAC 연산·판정·성능 측정 코드는 한 벌만 있습니다.

### 7. 패턴 생성기 (`pattern_maker.py`, 보너스)

메서드 하나가 크기와 모양을 받아 패턴을 만듭니다.

```python
PatternMaker.make_pattern(size, shape)   # shape 는 'Cross' 또는 'X'
```

모양별로 함수를 따로 두지 않고 하나로 합친 이유는, 두 모양의 차이가
"어느 칸을 1로 채우느냐" 한 줄뿐이기 때문입니다.

| 모양 | 1로 채우는 칸 |
| --- | --- |
| `Cross` | `row == 가운데` 또는 `col == 가운데` |
| `X` | `row == col` 또는 `row + col == size - 1` |

나머지 반복문과 검사 코드는 완전히 같아서, 함수를 둘로 나누면 그 부분이 그대로 복제됩니다.
`shape` 값도 새로 만들지 않고 프로그램 표준 라벨(`Cross` / `X`)을 그대로 써서,
판정 결과와 바로 비교할 수 있게 했습니다.

**검증**: 생성기가 만든 패턴이 `data.json`의 패턴 8개와 모두 정확히 일치합니다.

```
size_3_1  size=3   shape=X      -> 일치
size_3_2  size=3   shape=Cross  -> 일치
...
8 / 8 일치
```

알아둘 점이 두 가지 있습니다.

- `N = 1`이면 십자가와 X가 똑같은 `[[1.0]]`이 됩니다. 두 점수가 같아져 `UNDECIDED`가 나오는데,
  이는 오류가 아니라 1x1에서는 두 모양이 실제로 구별되지 않기 때문입니다.
- `N`이 짝수면 가운데 칸이 없어 십자가가 한쪽으로 치우칩니다.
  과제에서 쓰는 크기(3, 5, 13, 25)는 모두 홀수라 문제가 없습니다.

## 결과리포트

### 실행 결과 요약

```
총 테스트: 8개
통과: 5개
실패: 3개

실패 케이스:
- size_5_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL
- size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 FAIL
- size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL
```

### 실패 원인 분석

실패한 3건은 모두 같은 원인이며, 코드의 버그가 아니라 **데이터가 수학적으로 동점이기
때문에 생긴 결과**입니다. 원인을 "데이터/스키마 문제", "로직 문제", "수치 비교 문제"로
나눠 보면 이번 실패는 전부 **수치 비교 문제**에 해당합니다.

각 케이스의 실제 점수는 아래와 같습니다.

| 케이스 | Cross 점수 | X 점수 | 두 점수 차이 | expected | 판정 |
| --- | --- | --- | --- | --- | --- |
| size_5_1 | 0.9 | 0.8999999999999999 | 1.1e-16 | X | UNDECIDED |
| size_13_2 | 7.499999999999997 | 7.5 | 2.7e-15 | Cross | UNDECIDED |
| size_25_1 | 4.9 | 4.899999999999999 | 1.8e-15 | X | UNDECIDED |

세 케이스 모두 두 점수의 참값이 정확히 같습니다. 화면에 보이는 `0.9`와
`0.8999999999999999`의 차이는 십진수 `0.1`을 2진 실수로 정확히 표현할 수 없어서
곱셈과 덧셈을 반복하는 동안 쌓인 부동소수점 오차일 뿐, 의미 있는 점수 차이가 아닙니다.

그래서 epsilon 없이 `if cross_score > x_score:` 처럼 그냥 비교하면
승자가 "데이터"가 아니라 "누적 오차의 방향"에 따라 정해집니다. 실제로 세 케이스를
epsilon 없이 계산해 보면 size_5_1은 Cross, size_13_2는 X, size_25_1은 Cross로 나오는데,
셋 다 expected와 다릅니다. 즉 epsilon을 빼도 통과하지 못하며, 우연히 방향이 맞았더라도
그것은 정답을 맞힌 것이 아니라 오차 방향이 우연히 일치한 것에 불과합니다.

정리하면, epsilon 정책은 실패를 만들어낸 원인이 아니라 **원래 판정할 수 없는 입력을
"판정할 수 없다"고 정직하게 보고하게 만든 장치**입니다. 만약 실패를 0으로 만들고 싶다면
비교 로직을 고칠 게 아니라, 데이터를 동점이 아니게 만들거나(필터 가중치 조정)
"동점일 때는 특정 라벨을 고른다" 같은 별도의 tie-break 규칙을 과제 명세에 추가해야 합니다.
지금 명세에는 그런 규칙이 없으므로 UNDECIDED → FAIL이 규칙에 맞는 동작입니다.

나머지 5건은 두 점수 차이가 epsilon(1e-9)보다 압도적으로 크기 때문에
오차와 무관하게 안정적으로 PASS합니다.

| 케이스 | Cross 점수 | X 점수 | 두 점수 차이 |
| --- | --- | --- | --- |
| size_3_1 | 1.0 | 5.0 | 4.0 |
| size_3_2 | 5.0 | 1.0 | 4.0 |
| size_5_2 | 8.9 | 0.1 | 8.8 |
| size_13_1 | 0.3 | 14.7 | 14.4 |
| size_25_2 | 52.9 | 0.1 | 52.8 |

여기서 짚어 둘 점은, 실패를 가른 것이 "필터에 소수점 값이 있느냐"가 아니라는 것입니다.
`size_5_1`(FAIL)과 `size_5_2`(PASS)는 **같은 size_5 필터**를 씁니다. 차이는 패턴 쪽입니다.

`size_5_1`의 X 패턴을 예로 보면, Cross 필터와는 가운데 한 칸(`0.9`)만 겹쳐서 0.9점이 되고,
X 필터와는 대각선 9칸(`0.1` × 9)이 겹쳐서 역시 0.9점이 됩니다.
`0.9 = 0.1 × 9`가 되도록 필터 값이 짜여 있어, 두 점수가 **설계상 정확히 같아지는** 입력입니다.

정리하면 부동소수점 오차는 실패의 원인이 아니라 증상입니다.
원인은 두 점수가 동점이 되도록 만들어진 입력이고, 오차는 그 동점을
`0.9` vs `0.8999999999999999`처럼 "동점이 아닌 것처럼" 보이게 만들 뿐입니다.
크기 3의 두 케이스는 값이 0과 1뿐이라 오차가 아예 생기지 않지만,
설령 소수점 값이 있었더라도 점수 차이가 4.0이라 판정은 흔들리지 않았을 것입니다.

데이터/스키마 문제와 로직 문제도 따로 확인했습니다. 일부러 망가뜨린 `data.json`
(크기가 다른 패턴, `expected` 누락, 알 수 없는 라벨, 필터가 없는 크기)으로 실행한 결과,
프로그램이 중단되지 않고 해당 케이스만 사유와 함께 FAIL로 기록한 뒤 끝까지 진행했습니다.

### 시간 복잡도 분석

측정 결과는 다음과 같습니다. (10회 평균)

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | 1회 연산당 시간(µs) |
| --- | --- | --- | --- |
| 3x3 | 0.0010 | 9 | 0.111 |
| 5x5 | 0.0020 | 25 | 0.080 |
| 13x13 | 0.0101 | 169 | 0.060 |
| 25x25 | 0.0345 | 625 | 0.055 |

MAC 연산은 N행 × N열을 한 칸도 빠짐없이 훑기 때문에 곱셈과 덧셈이 정확히 N²번
일어납니다. 따라서 시간 복잡도는 **O(N²)** 입니다. N이 2배가 되면 시간은 약 4배가 됩니다.

측정값도 이를 뒷받침합니다. 13x13 → 25x25 구간을 보면 연산 횟수는 169 → 625로 3.70배
늘었고, 측정 시간은 0.0101 → 0.0345로 3.42배 늘어 거의 일치합니다.

반면 3x3 → 5x5 구간은 연산 횟수가 2.78배 늘었는데 시간은 2.0배만 늘어 예측보다 적게
증가합니다. 이는 N이 작을 때는 실제 계산보다 **함수 호출과 반복문 준비에 드는 고정
비용**이 차지하는 비중이 커서 생기는 현상입니다. 표의 마지막 열(1회 연산당 시간)이
0.111 → 0.080 → 0.060 → 0.055µs로 점점 줄다가 일정한 값에 수렴하는 것이 그 증거입니다.
N이 충분히 커지면 고정 비용은 무시할 수 있는 수준이 되고 순수 O(N²) 곡선에 가까워집니다.

이 결과가 NPU가 필요한 이유를 보여줍니다. 25x25만 해도 한 번에 625번의 MAC이
필요한데, 실제 AI 모델은 이런 필터를 수천 개씩 사용합니다. 예를 들어 1024x1024 입력
하나만 해도 100만 번이 넘는 MAC이 필요하고, CPU처럼 한 번에 하나씩 순서대로 처리하면
시간이 감당되지 않습니다. 그래서 수천 개의 MAC을 동시에 처리하는 전용 하드웨어(NPU)가
등장했습니다.
